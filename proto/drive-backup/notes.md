# drive-backup — 案 A（バックアップ型）の UI/UX 設計

[proto/drive-photos](../drive-photos/) の比較で **案 A** を採用。ここはその詳細設計。

**案 A の一文**: 写真は今までどおりアプリに保存し、**控え**をユーザーの Google ドライブに作る。
表示は常にアプリ側なので、連携してもしなくても、切っても、**見た目は何も変わらない**。

プロト: [`index.html`](./index.html)（画面 × 状態 × 権限を切替可）

## 何を確かめたいか

1. **バックアップの状態をどれだけ見せるか。** 「正常は無音」で不安にならないか。
   済みバッジを出す / 出さないをプロト設定で切り替えて実機で比べる
2. **「アプリを開いている間だけ進む」**という制約の伝え方。不信感にならないか
3. **連携前の説明**で「ドライブの他のファイルは読まない」が伝わるか（信頼の入口）
4. 初回の案内カードがアルバム上部に出るのは邪魔でないか
5. 失敗・連携切れ・ドライブ容量不足のとき、**「アプリの写真は無事」**が伝わるか

---

## UI/UX の設計判断

### 判断 1: 「正常は無音、異常だけ知らせる」

状態表示は 3 つ（済み / 待ち / 失敗）あるが、**日常画面では出さない**。

| 場所 | 済み | 待ち | 失敗 |
| --- | --- | --- | --- |
| アルバム一覧 | 出さない | 出さない | 出さない |
| 記録詳細 | **要検討**（プロトで切替） | ごく小さく | 出す＋再試行 |
| バックアップ画面 | **ここに集約** | ここに集約 | ここに集約 |

バックアップは背景の仕事で、保存はすでに成功している。写真 1 枚ずつに「済み」を出すと、
**うるさいうえに「済みでない写真がある」ことを常に意識させて不安を生む**。
「知りたくなったら 1 箇所を見れば全部わかる」を保証したうえで、日常は静かにする。

> ただし「本当にバックアップされてる？」という不安は実在する。
> **済みバッジを出す / 出さないは実機で比べて決める**（プロト設定）。

### 判断 2: 用語は「バックアップ」。「同期」と呼ばない

「同期」は双方向を想起させ、「ドライブで消したらアプリからも消えるの？」という
誤解を生む。案 A は**一方向のコピー**なので「バックアップ」が正確。
「連携」は接続そのものを指すときだけ使う。

| 使う | 使わない |
| --- | --- |
| バックアップ / 控え | 同期・シンク |
| 連携する / 解除する | 認証・認可・トークン |
| うまくいかなかった写真 | エラー・失敗件数・リトライ |

### 判断 3: バックアップされるのは「自分が追加した写真」だけ

世帯の全写真を自分のドライブへ入れると、**他人が撮った写真が自分のドライブに現れる**。
これは驚きであり、説明も面倒になる（誰の容量を使う？ 退出したら？）。

- **既定かつ唯一の挙動: 「あなたが追加した写真」**
- 一文で説明できる。驚きがない。世帯全体を残したければ**各自が連携すれば全体が埋まる**
- owner だけ「世帯すべて」を選べる案は**却下**。分岐が増えて説明が難しくなる（複雑さを避ける方針）

### 判断 4: 「アプリを開いている間だけ進む」を隠さない

Vercel Hobby にジョブ基盤が無いので、一括バックアップはクライアント駆動になる。
**これは隠さず、代わりに「やめても失われない」を必ず添える。**

> このページを開いたままにしてください。
> 閉じても、次に開いたとき**続きから再開**します。

新規の写真は数枚なので一瞬で終わる。この説明が要るのは**初回の一括だけ**。

### 判断 5: 置き場所はメニュー直下 1 階層

D33 のボトムタブ（ホーム / カレンダー / ＋ / アルバム / メニュー）の
**メニュー直下**に「写真のバックアップ」を置き、右側に現在の状態を出す。
設定の奥に埋めない（体重・設定が 3 段奥にあって使われなかった前例がある）。

### 判断 6: 発見はアルバム上部に 1 回だけ

写真の文脈で出すのが自然。**dismiss したら二度と出さない**（メニューには常設）。
記録の保存直後に出すのは却下 —— 保存の達成感を邪魔する。

### 判断 7: viewer には出さない

バックアップは「世帯の写真を個人のドライブへ持ち出す」行為。
viewer（祖父母など閲覧のみ）に出すと、閲覧権限しかない人がデータを複製できてしまう。
**owner / editor のみ。** ゲスト（保育園・シッター）は対象外。

### 判断 8: 技術用語を一切出さない

quota・API・トークン・リトライ回数は出さない。
「12 件のエラー」ではなく「**12 枚がバックアップできませんでした**」。

### 判断 9: 異常時は必ず「アプリの写真は無事」を書く

案 A の最大の強みは**表示経路を触っていないこと**。異常が起きても写真は見える。
それが伝わらないと強みが消えるので、**すべての異常表示に一文入れる**。

| 異常 | 必ず添える一文 |
| --- | --- |
| 連携が切れた | ドライブの写真は残っています。アプリの表示にも影響はありません |
| ドライブの容量不足 | アプリの中の写真はすべて無事です |
| 一部が失敗 | アプリの写真は無事です。控えだけが作れていません |

### 判断 10: アプリの空き容量を出す（案 B への布石）

案 A 唯一の弱点は Supabase Free 1GB の壁。**壁は突然来てはいけない。**

- バックアップ画面の下部に「アプリの空き容量」メーターを常設
- **6 割を超えたら**「原本をドライブへ移して空ける方法もあります」の案内を出す
  （＝ 第 3 段＝案 B へ進む判断のトリガーが、ユーザーにも開発にも同時に見える）
- 6 割未満のときは案内を出さない（今は関係ない情報を出さない）

## 画面と状態

| 画面 | 役割 |
| --- | --- |
| アルバム | 発見（1 回だけの案内カード） |
| 連携の説明 | 同意前に何が起きるかを説明する。**信頼の入口** |
| バックアップ | 状態の集約。連携・一括・進捗・異常・解除の入口 |
| 記録詳細 | 写真ごとの状態（控えめ） |
| メニュー | 常設の導線 ＋ 一目でわかる状態 |
| 解除の確認 | 「何が起きないか」を書く |

バックアップ画面の状態:

| 状態 | 出すもの |
| --- | --- |
| 未連携 | 連携の案内 |
| 連携直後 | これまでの写真 N 枚 →「今すぐバックアップする」＋ 所要の予告 |
| 実行中 | 進捗（枚数＋バー）／「開いたままに」／一時停止 |
| 平常（済み） | すべてバックアップ済み ＋ 最終時刻 ＋ 自動バックアップのトグル |
| 一部失敗 | N 枚が失敗 ＋ もう一度試す ＋「アプリの写真は無事」 |
| 連携切れ | 再連携 ＋「表示に影響なし」 |
| ドライブ容量不足 | ドライブの容量確認へ ＋「アプリの写真は無事」 |

## 決めていないこと

- **済みバッジを記録詳細に出すか**（実機で比較して決める）
- 自動バックアップの既定値（連携したら ON でよいか、明示的に選ばせるか）
- Wi-Fi のときだけ実行する選択肢を出すか（PWA から回線種別は取れるが精度が低い）
- 一括バックアップ中に画面を離れたときの復帰導線（メニューの状態表示で足りるか）
