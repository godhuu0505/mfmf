# プロトタイプ駆動をなぜこの形にしたか

新機能の画面・挙動を先に形にして合意し、そこから仕様を確定して実装に入る。
その「先に形にする」手段として **使い捨てブランチの実コードプロトタイプ**を選んだ理由と、
却下した案を残します。

手順そのものは `.claude/skills/prototype/SKILL.md` が正です（本書は「なぜ」だけを扱います）。
関連: [design-decisions.md](./design-decisions.md) / [decisions.md](./decisions.md)

---

## 1. 解決したい課題

### 1-1. 画面の形を決める場所が、フローのどこにも無い

現行フローは
`vision-and-roadmap.md`（機能カタログ）→ `phase-N-use-cases.md`（UC-xx ＋受け入れ条件＋D 決定ログ）
→ GitHub Issue → PR → main マージ＝本番リリース。

**この鎖に UI/UX の成果物が 1 つも無い。** 数えるとはっきりする:

| | 件数 |
| --- | --- |
| UC の総数 | 48 |
| 受け入れ条件に RLS / サーバー語彙（RLS・pgTAP・deny・ポリシー等）を含む UC | 17 |
| 受け入れ条件に画面 / UI 語彙を含む UC | 6 |
| うち**画面の形**に踏み込んでいるもの | 実質 2（UC-A01 / UC-A06） |

しかもその 2 件はどちらも「**サーバー強制が一次防衛線。UI は補助**」と明記されている。
つまり **48 個のユースケースを書いても、画面がどうあるべきかは 1 行も決まらない**。

これは Phase 3.5 が「テナント分離・認可・招待」というバックエンド中心のフェーズだったので、
当時は正しい形だった。問題はこれからのフェーズで顕在化する。

### 1-2. 実際に「🟡 のまま止まる」現象が起きている

`vision-and-roadmap.md` §5 の機能カタログは 🟢 採用 25 件に対し **🟡 検討中が 11 件**。
その 11 件を並べると、**10 件が「UI の形が決まらないと進めない」もの**だと分かる。

```
クイック記録 / 写真ドリブン入力 / オフライン下書き / タグ・マイルストーン /
月次ダイジェスト / 日程調整 / 通院・服薬 / 共有レポート / 健康サマリー / 共有アルバム
（UI 起因でない 🟡 は「自動テスト」の 1 件のみ）
```

これらが 🟡 に滞留しているのは、優先度が低いからではなく
**現行のフォーマットでは決めようがないから**。
「ごはん/トイレ/散歩をボタンタップだけで構造化記録」（クイック記録）が
良いかどうかは、受け入れ条件を何行書いても判断できない。

**Phase 3.5 が完了し、次に控えるのはレポート・アルバム・予定・入力体験** ——
いずれも UI 比重の高い領域。この詰まりは今後さらに悪化する。

### 1-3. 文章仕様では原理的に伝わらないものがある

Markdown の仕様書は情報は伝えられるが、**画面レイアウトと触り心地は伝えられない**。
mfmf は PWA で、価値は「スマホで片手で、片手間に記録できるか」に集中している。

- 片手で親指が届く位置にボタンがあるか
- セーフエリア（ノッチ・ホームインジケータ）に被らないか
- IME が立ち上がったときにフォームが隠れないか
- スタンドアロン表示（ホーム画面から起動）でナビゲーションが破綻しないか
- 記録が 0 件のとき / 200 件あるときに画面が成立するか

これらは文章でも Figma でも評価できず、**実機で触るしかない**。
そして評価を実装後まで先送りすると、作り直しのコストは実装前の何倍にもなる。

### 1-4. ただし「モック作りに時間がかかる」なら本末転倒

課題 1-1〜1-3 を解決するために新しい工程を足すのだから、
その工程自体が重ければ意味がない。**スピードと情報量の両立が要件**であり、
「モックを作るために時間を使う」形は採用できない。
これが静的 HTML 案を却下した直接の理由（→ §2）。

### 1-5. ドキュメントが実際に腐っていて、しかも実害がある

調査中に、S1〜S5 完了済みなのに古いままの記述が **6 箇所**見つかった。

| ファイル | 誤った記述 |
| --- | --- |
| `CLAUDE.md` | 「共有方針 (A): `household_id` は持たず `owner_id (= auth.uid())` ベースで RLS」 |
| `AGENTS.md` | 同上 |
| `design-decisions.md` | 同上（§共有方針・§セキュリティ） |
| `README.md` | 「**Google OAuth 一本化**（メール/パスワードログインは使えません）」 |
| `architecture.md` | 画面表に `/onboarding` `/invite/[token]` `/guest` `/signup` `/help` が無い。データモデル表に `households` / `household_members` / `guest_grants` / `household_invites` が無い |
| `features.md` | households / ゲスト / 招待に一切言及なし |

このうち **`CLAUDE.md` / `AGENTS.md` は毎セッション読み込まれる**ため、実害の質が違う。
`AGENTS.md` は Copilot / Cursor / Codex も読む。想定される具体的な事故:

- エージェントが「RLS は `owner_id = auth.uid()`」と信じて migration を書く
  → 世帯メンバーに見えるべき行が見えなくなる、あるいは逆に
  `owner_id` 一致だけで write を許して **owner/editor/viewer の role 制御を素通り**させる
- **RLS はこのアプリのセキュリティの一次防衛線**（CLAUDE.md 自身がそう宣言している）なので、
  ここの誤情報は直接セキュリティに効く

これは「ドキュメントが古い」問題ではなく、**バグ**として扱うべきもの。

### 1-6. 同じ事実が 2 箇所以上に書かれている（二重管理）

| 事実 | 置き場所 A | 置き場所 B | 結果 |
| --- | --- | --- | --- |
| 画面一覧 | `CLAUDE.md`（正確だった） | `architecture.md`（5 画面欠落） | 片方が腐った |
| 機能一覧 | `docs/reference/features.md` | アプリ内 `/help`（`src/app/help/page.tsx`, 233 行） | 片方が腐った |
| データモデル | `architecture.md` の表 | `supabase/migrations/`（31 本） | 片方が腐った |

**二重管理されているものは、必ずどちらかが腐る。** 例外なくそうなっていた。
ここにモックという 4 つ目の UI 記述を足せば、腐敗候補が 1 つ増えるだけになる。

### 1-7. 「何を残し、何を残さないか」の基準が無い

基準が無いのでドキュメントは増える一方で、増えれば腐る。
逆に、**却下した案とその理由はどこにも残っていない**。
コードは採用された案しか語らないので、これは書かなければ永久に失われ、
半年後に同じ議論を再演することになる。

### 1-8. 開発速度と「手で同期する工程」は構造的に両立しない

直近の commit は **1 日あたり 10〜16 本**（S3 / S4 / S5 が約 3 日で完了）。
コミッタは実質 1 人 ＋ Claude。

この速度で「実装したらドキュメントも直す」という手動同期を要求すれば、必ず飛ばされる。
実際 `design-decisions.md` は 6/30 で止まり、7 月の S3/S4/S5 実装中に一度も更新されなかった。
**規律の問題ではなく、速度と手動同期の構造的な非互換**として扱う必要がある。

---

以上をまとめると、解決すべきは次の 3 点になる。

1. **UI を決める手段を用意する**（1-1 / 1-2 / 1-3）——ただし軽量に（1-4）
2. **新しい腐敗候補を増やさない**（1-6 / 1-8）
3. **残す価値のある情報だけを残す基準を決める**（1-5 / 1-7）

## 2. 却下した案 A: `mocks/` に静的 HTML を置く

最初に検討した案。HTML / CSS / JS だけで画面を組み、リポジトリの `mocks/` に置いて残す。

**却下理由 1: mfmf では実装プロトタイプの方が速い。**
`src/app/gallery/page.tsx` は 99 行で、**約半分がデータ取得**。固定配列に差し替えれば 50 行前後で画面が立つ。
`AppHeader` / `PhotoGallery` / `RecordForm` / デザイントークン / ダークモード / セーフエリア /
フォーカスリングは**すべて `import` で手に入る**。
同じ画面を静的 HTML で作ると markup と JS を書き起こすことになり、しかも**実装時に 100% 捨てる**。
既存コンポーネントが十分に育った今のリポジトリでは、「モックの方が速い」という前提が成り立たない。

**却下理由 2: 情報量が足りない。**

| 得たい情報 | 静的 HTML | 使い捨てブランチ |
| --- | --- | --- |
| レイアウト・配色 | ○ | ○ |
| 画面遷移 | △ 手で `href` を繋ぐ | ◎ 本物 |
| 空 / 大量 / エラー状態 | △ 手で複製 | ◎ 配列を差し替えるだけ |
| ダークモード | △ | ◎ 自動追従 |
| **実機 PWA の触り心地**（セーフエリア・IME・片手操作） | **×** | ◎ |
| 実装への持ち込み | × 全捨て | ◎ そのまま育てられる |
| 3 案の並列比較 | ◎ | △ → 1 ブランチ内の複数ルートで解決 |
| ゼロからのラフスケッチ | ◎ | △ → 発散段階はリポジトリ外で解決 |

静的 HTML が勝つ 2 項目は、どちらも**リポジトリに置く必要がない**。

**却下理由 3: 7 個目の腐敗候補になる**（→ §4）。

**却下理由 4**: Claude Code 作者 Boris Cherny の発言が否定しているのは、PRD **と静的モックの両方**だった。

> *"There's just no way we could have shipped this if we started with **static mocks** and Figma **or** if we started with a PRD."*

代わりに置かれたのは**動くプロトタイプ**であって、モックではない。

## 3. 却下した案 B: Spec Kit / Kiro / OpenSpec の導入

仕様駆動開発ツールで requirements / design / tasks を生成させる案。

**却下理由**: n=1 の個人プロジェクトには過剰。
Scott Logic が同一機能を 2 通りで実装した実測では、Spec Kit 側が Markdown 2,500 行・
人間レビュー 3.5 時間で**約 10 倍遅く**、*"duplicative documentation without improving code quality
or reducing bugs"* と結論している。marmelab は「現在日時を表示するだけで 8 ファイル 1,300 行の Markdown」を報告。

既存の `UC-<領域><連番>` ＋ D 決定ログが、既に十分軽い仕様フォーマットとして機能している。

## 4. なぜ「腐るもの」と「腐らないもの」に分かれたか

§1-5 で挙げた陳腐化に対して、**腐らなかったドキュメントもある**。
その差を見ると、モックをどう扱うべきかが決まる。

| ドキュメント | commit 数 | 最終更新 | 状態 |
| --- | --- | --- | --- |
| `phase-3-5-use-cases.md`（決定ログを含む） | 16 | 2026-07-05 | **正確** |
| `design-decisions.md` | 4 | 2026-06-30 | 陳腐化 |
| `AGENTS.md` | — | 2026-06-30 | 陳腐化 |

**腐った側は、全部「誰も読まないもの」だった。**
腐敗は規律不足の証拠ではなく、そのドキュメントが不要だった証拠。
7 月に S3/S4/S5 を実装したとき `design-decisions.md` を一度でも開いていれば、嘘に気づいていたはず。
気づかなかったのは、開く必要がなかったから。

一方 `phase-3-5-use-cases.md` が生き残ったのは、**荷重がかかっていた**から:

- Issue（S1〜S5）へ落とすときの元ネタになっている
- **直近 60 commit のうち 12 件が `UC-xx` / `Dx` を件名で引用**している
- §7「未決事項」が、後のフェーズで読み返される前提で書かれている

つまり「良いドキュメントだから残る」のではなく、
**日常の作業に組み込まれているものだけが残る**。§1-8 の速度を踏まえれば、
善意や規律で腐敗を止められないことも明らか。

→ 結論は 2 つ。
**(a) プロトタイプは「残さない」形にする**（永続化は決定ログ 1 行だけ。§1-6 の腐敗候補を増やさない）。
**(b) 残すと決めたものには荷重をかける**（決定ログは commit 件名から引用され続ける既存の慣習に乗せる）。

## 5. では、何を残すのか

情報を「コードから復元できるか」で分けると、残すべきものが決まる。

| 種類 | 例 | 復元可能？ | 方針 |
| --- | --- | --- | --- |
| 現状の仕様 | 画面一覧・機能一覧・データモデル | **可能**（AI が数秒で） | 書かない・維持しない |
| AI が毎回読む前提 | `CLAUDE.md` / `AGENTS.md` | 可能だが**コードより先に読まれる** | 最小限にし、古いものは**バグとして直す** |
| **決定と却下理由** | D1〜D14、未決事項 | **不可能** | **1 行で残す**（[decisions.md](./decisions.md)） |

コードは勝った案しか語らない。負けた案とその理由は、書かなければ永久に失われ、
半年後に同じ議論を再演することになる。

「過去の仕様を人間が読み返すフロー」が実在する証拠もこのリポジトリにある。
`76a2406 世帯削除(UC-H09 一部)とアイデンティティ連携の方針確定（#117 §3・§4）` は、
半年前に §7「未決事項」へ書いておいた論点を読み返して決着させたコミット。
読み返されるのは**未決事項と却下理由**であって、現状の仕様ではない。
