# drive-photos — 写真を Google ドライブに保存する

ログイン中ユーザーの Google アカウントのドライブに写真を保存できるようにする。
**保存先の決め方**（毎回選ぶ / 後から連携 / 最初から引っ越し）と、**4 つの在りか**
（両方 / アプリだけ / ドライブだけ / どちらにも無い）の表示を決めるためのプロト。

プロト: [`index.html`](./index.html)（案 A/B/C ＋ 在りか・連携状態・権限・原本の持ち主を切替可）

## 何を確かめたいか

1. **保存のたびに保存先を選ばせるのは重すぎないか**（案 C の記録フォーム）。
   写真を残す手数が増えると、このアプリの目的（続けられること）と正面から衝突する
2. **「どちらにも無い」の文言**が、家族から見て「アプリが写真を消した」に読めないか（4 状態タブ）
3. **バッジの情報量**。一覧に保存先バッジが並ぶ案 C がうるさくないか（アルバム）
4. 案 B の「サムネはアプリ・原本はドライブ」が、**タップして原本が出るまでの待ち**込みで成立するか
5. 「たろうさんが連携を切ると、たろうさんが入れた写真の原本だけ見えなくなる」を
   **家族に説明できるか**（プロト設定「原本の持ち主」＝各自 / owner 集約）

## 現状（コード調査）

Drive 連携は**土台だけ既にある**。ゼロからではない。

| ある | 場所 |
| --- | --- |
| `drive.file` スコープ付き Google OAuth（`access_type=offline` + `prompt=consent`） | `src/app/login/LoginForm.tsx` |
| refresh token を AES-256-GCM で暗号化して保存 | `src/app/auth/callback/route.ts` / `src/lib/google/crypto.ts` |
| `google_credentials` テーブル（owner_id ベース RLS） | `supabase/migrations/20260616130711_google_credentials.sql` |
| 保存済み refresh token から access token を発行 | `src/lib/google/token.ts` |
| セットアップ手順 | `docs/guides/google-drive-setup.md` |

**無いもの**: Drive へのアップロード、`record_photos` の Drive 対応列、画像プロキシ、設定 UI。
写真は今も Supabase Storage（private・署名付き URL・`{household_id}/{record_id}/{file}`）だけ。

引っかかる既存の制約:

- **Vercel の Function ボディ上限 4.5MB** → 画像本体をサーバー経由で送れない。
  Supabase Storage と同じく**クライアントから Drive へ直接アップロード**する形になる
  （Drive API は CORS 対応。resumable upload をブラウザから叩ける）
- **Service Worker は private / 期限付き URL をキャッシュしない**（`public/sw.js` の不変条件）。
  Drive 原本のプロキシ URL も同じ扱いにする
- `getGoogleAccessToken()` は**呼ぶたびに Google のトークンエンドポイントを叩く**。
  プロキシ配信で使うと 1 枚表示 = 1 リフレッシュになる。`expires_in`（約 1 時間）内は
  使い回すキャッシュが要る（実装時の必須項目）

## 3 案

### 案 A: バックアップ型（アプリが正・ドライブは控え）

保存は今まで通り Supabase。保存後にバックグラウンドでドライブにも控えを作る。**表示は常にアプリ側**。

- 一覧・詳細のドライブ通信は **0**。ドライブを叩くのは保存時と一括バックアップ時だけ
- 「ドライブだけにある」状態が**原理的に起きない**ので、状態が実質 3 つに減る
- 連携を切っても表示が何も変わらない（説明が一番簡単）
- ✗ **容量問題を解決しない。** Supabase Free の 1GB は同じ速度で減る
- ✗ 同じ画像を 2 か所に持つ（思い出の単一障害点対策としては正しい）

### 案 B: 引っ越し型（ドライブが正・サムネだけアプリ）

保存時にクライアントで長辺 1600px のサムネを作って Supabase へ、原本はドライブへ直接。
一覧・詳細はサムネ、タップしたときだけプロキシ経由で原本。**`roadmap.md` §4 の当初構想**。

- **容量問題が本当に解決する**（アプリ 32MB / ドライブ 1.8GB のような比率になる）
- 一覧のドライブ通信は **0**（サムネはアプリ側）
- **「どちらにも無い」がいちばん軽い**。原本が消えてもサムネが残るので、写真自体は見える
- 未連携ユーザー・ゲスト（保育園）の写真は原本がアプリに残る = 混在は**正常な状態**として設計に織り込む
- ✗ 原本を開くたびにプロキシ（Vercel Function）を通る。待ちが発生する
- ✗ 実装がいちばん重い（アップロード・プロキシ・サムネ生成・移行バッチ）

### 案 C: 毎回選ぶ型（保存時に保存先を選択）

記録フォームに「アプリ / ドライブ / 両方」のセグメント。

- いちばん自由。ユーザーが完全に制御できる
- ✗ **保存のたびに選択が挟まる。** 写真を残す手数として重い
- ✗ 写真ごとに在りかが違うので、一覧にバッジが要り、**4 状態が本当に全部混ざる**
- ✗ 「ドライブのみ」の写真は一覧でも都度取得が要る（プロトのメーターで通信回数が増えるのが見える）
- ✗ 家族で設定がばらつくと「あの写真どこ？」が起きる

> 案 C は却下候補として作った。ただし**実機で触ってから**決めたい ——
> 「毎回選べる方が安心」という感覚がありうる。

## 4 状態の表示（案ごと）

| 在りか | 案 A | 案 B | 案 C |
| --- | --- | --- | --- |
| **両方** | 通常表示＋「バックアップ済み」 | サムネ表示＋「原本を表示」 | 通常表示＋「保存先: 両方」 |
| **アプリだけ** | 通常表示＋「バックアップ待ち」 | 通常表示＋「原本: アプリ内」（ゲスト・未連携は正常） | 通常表示＋「保存先: アプリ」 |
| **ドライブだけ** | **起きない** | 原本を縮小して表示（この 1 枚だけ通信） | 都度取得。連携が切れると即見えなくなる |
| **どちらにも無い** | 欠落カード＋復旧導線 | **サムネは残る**ので写真は見える。原本だけ開けない | 欠落カード。原因が写真ごとに違い説明が難しい |

**「どちらにも無い」は原因を書き分ける。** ここが UI のいちばんの肝で、原因は 3 つ：

1. ドライブでファイルが削除された（→ **ゴミ箱に残っている**ことが多い）
2. 連携が切れている（→ 原本は無事。**再連携すれば戻る**）
3. アップロードが完了していなかった（→ 入れ直す）

「表示できません」だけだと **mfmf が写真を消したように見える**。
「mfmf が写真を削除することはありません」を明記し、原因別の導線を出す。

権限: **viewer には同期・移動・再アップロードのボタンを出さない**（表示だけ）。
ゲスト（保育園・シッター）は Drive 連携の対象外。

## Google Drive API のレートリミット

出典: [Usage limits](https://developers.google.com/workspace/drive/api/guides/limits)。
2026-05-01 以降に作られた Cloud プロジェクトは**重み付き quota unit モデル**。

| 項目 | 値 |
| --- | --- |
| プロジェクト全体 | **1,000,000 units / 分** |
| ユーザーあたり（プロジェクト内） | **325,000 units / 分** |
| 読み取り（`files.get`） | 5 units |
| 一覧（`files.list`） | **100 units** |
| **ダウンロード** | **200 units** |
| 編集（`files.update`） | 50 units |
| 1 日のアップロード量 | 750 GB / ユーザー |
| 1 日の下り転送量 | 1 TB / プロジェクト（超過で課金対象） |

### 効いてくるのはどこか

**結論: 一覧をドライブから描かない限り、レートリミットは実質的な制約にならない。**

- ユーザーあたり 325,000 units/分 = **ダウンロード 1,625 回/分**。家族数人の利用では当たらない
- 危ないのは**一覧をドライブから描く設計**。アルバムを 200 枚スクロール = 40,000 units、
  しかもスクロールのたびに増える。→ **サムネは必ず Supabase に置く**（案 A / 案 B は 0 通信）
- `files.list` は 100 units と高い。**`drive_file_id` を DB に持ち、Drive を検索しない**
- **既存写真の一括バックアップがいちばんの山**。1,200 枚 = 約 60,000〜120,000 units。
  units は 1 分に収まるが、**Vercel Hobby には実行時間上限があり、cron / キューも無い**。
  → サーバーのバッチ処理では成立しない。**画面を開いている間にクライアントが少しずつ
  進める＋チェックポイントで再開**する形にする（プロトのドライブ設定画面）
- 403 `userRateLimitExceeded` / 429 は**指数バックオフ**（`min((2^n)+ランダムms, 32〜64秒)`）で再試行。
  同時アップロードは 2〜3 本に絞る

### レートリミットより先に効く制約

- **Vercel Hobby の帯域・関数実行**。原本をプロキシすると全バイトが Function を通る。
  1 枚 3MB × 1 日 100 枚 = 300MB/日。ここが Drive の quota より先に痛む
  → 原本を開くのは**タップしたときだけ**にする（案 B の設計）
- **アクセストークン発行**。`getGoogleAccessToken()` を 1 リクエスト 1 回叩くと、
  Google の OAuth エンドポイントへの往復がそのまま表示遅延になる。約 1 時間キャッシュする

## もう一つの軸: 誰のドライブに入れるか（[D10](../../docs/explanation/phase-3-5-use-cases.md) の未決事項）

ドライブは**個人**のもの、mfmf は**世帯**のもの。ここが最大のねじれで、3 案のどれを選んでも決着が要る。

| | 各自のドライブ（分散） | owner のドライブに集約 |
| --- | --- | --- |
| 容量 | 各自の 15GB を使える | owner の 15GB を全員で使う |
| 説明のしやすさ | 「入れた人のドライブ」＝ばらつく | 置き場所が 1 つで分かりやすい |
| 連携解除の影響 | その人が入れた原本だけ見えなくなる | owner が抜けると**全員が原本を失う** |
| 実装 | 各メンバーの refresh token で配信 | 共有フォルダへの書き込み（ファイルの所有者は作成者のまま） |

> `drive.file` スコープでは「アプリが作ったファイル」だけを扱える。共有フォルダに入れても
> **ファイルの所有者は作成者**なので、「owner に集約」は保存場所が揃うだけで所有権は揃わない。
> 所有権まで揃えるには `transferOwnership` が要り、スコープが広がる（`drive.file` では足りない）。

## 現時点の推し

**案 B（引っ越し型）＋ 分散（各自のドライブ）**を推す。理由は 3 つ。

1. **容量問題を実際に解決するのは案 B だけ。** 案 A は控えを作るだけで Supabase の 1GB は同じ速度で減る
2. **「どちらにも無い」がいちばん軽い。** サムネが残るので写真は見え続ける。案 A / C は写真が消える
3. `roadmap.md` §4 の当初構想と一致し、ドライブ通信も一覧 0・原本タップ時のみで**レートリミットに当たらない**

ただし段階的に入れる。**案 A の同期エンジンは案 B の部品と同じ**（クライアント直アップロード・
バックオフ・チェックポイント）なので、A → B は作り直しにならない。

1. **第 1 段**: 案 A 相当（新しい写真をドライブへバックアップ。表示は今まで通り）
   → 同期エンジンとエラー表示だけを先に固める
2. **第 2 段**: プロキシ配信 ＋ サムネ生成 ＋ 「原本をドライブへ移す」で案 B へ
3. **第 3 段**: 既存写真の一括移行（クライアント駆動・再開可能）

案 C（毎回選ぶ）は既定として採らない。**設定画面での 1 回きりの選択**にすれば、
案 C が持っていた「自分で決めたい」は満たせる。

## 未決事項

- **サムネ生成をどこでやるか**。`imageResize.ts` は既にブラウザで縮小しているので、
  保存時は流用できる。既存写真の一括移行時は「Supabase の原本を落として縮小して上げ直す」になる
- **プロキシのキャッシュ**。SW には載せない（不変条件）。HTTP キャッシュヘッダ
  （`private, max-age`）でブラウザキャッシュに載せるかは要検討
- **アクセストークンをブラウザに渡すか**。クライアント直アップロードには要る。
  `drive.file` なので影響範囲は「このアプリが作ったファイル」に限られるが、寿命と渡し方は決める
- **ゲスト（保育園）の写真**の扱い。ゲストは Drive 連携しないので原本はアプリに残る。
  後から世帯側でドライブへ移すかどうか
- **アプリ側で写真を削除したとき、ドライブの原本も消すか**。既定は「消さない」を推す
  （ドライブは利用者のものなので、アプリが勝手に消すのは驚きになる）
