# mfmf の原則（Mission / Vision / Values）

**この文書は「何を作るか」ではなく「どう判断するか」を扱います。**
個別の決定は [decisions.md](./decisions.md)（D ログ）に、機能の将来構想は
[roadmap.md](./roadmap.md) にあります。本書はその**上位にある判断基準**です。

Values は一般論ではありません。**すべて、実際に代償を払って learned したこと**です。
各項目に「何が起きたか」を付けてあります。抽象論に見えたら §Values の根拠を読んでください。

---

## Mission

> **保育園でのあの子と、おうちでのあの子。**
> **離れて過ごした時間もつないで、気づけば毎日が残っているようにする。**

家族はいつも一緒にいるわけではありません。送るのは片方、迎えるのはもう片方。
保育園は、家族が見ていない何時間かを見ています。
その断片が集まって、**はじめてその子の 1 日になります**。

だから鍵は「気づけば」です。頑張って書くものではなく、片手で、数秒で。
記録は完璧さではなく**続いた量**で価値が出ます。

## Vision

> **何年か経ってスクロールすると、あの子の毎日がそのまま流れていく。**
> **「こんなに小さかったんだ」と笑える。**
> **そして新しいアイデアは、思いついた日のうちに手のひらで触れる。**

前半は家族にとっての未来、後半は作り手にとっての未来です。
そしてこの 2 つは、実は同じことを要求しています。

- **何年経っても流れていく** ためには、記録も、記録を作った仕組みも古びていないこと
- **思いついた日に触れる** ためには、思いつきと実物の間に重い工程がないこと

Values はすべてここから導かれます。腐らせない・列挙しない・机上で止まらない ——
全部、**この 2 つの未来を守るため**の判断基準です。

## Values（根拠）

### V1. 腐らせない形でしか持たない

> 手で同期する文書は必ず腐る。持つなら生成する。生成できないなら持たない。

**起きたこと**: 陳腐化していた記述が最終的に **14 箇所**見つかりました。
そして**二重管理していたものは、例外なく片方（または両方）が腐っていました**。

| 事実 | 置き場所 A | 置き場所 B | 結果 |
| --- | --- | --- | --- |
| 認証方式 | `README.md` | `local-supabase.md` | **両方**腐っていた |
| Drive 保存の有無 | `google-drive-setup.md` | `LoginForm.tsx` | **両方**腐っていた |
| Storage パス規約 | `CLAUDE.md` | `storagePath.ts` | **両方**腐っていた |

腐った側は全部「誰も読まないもの」でした。生き残ったのは、
**荷重がかかっていたもの**（commit 件名から参照され続けたもの）だけです。

**帰結**: [D16](./decisions.md) は当初「腐るから持たない」でしたが、
[D26](./decisions.md) で「**腐る条件は人間が手で同期することであって、存在すること自体ではない**」
と精緻化しました。生成が自動なら持てます。

### V2. 列挙ではなく原則で守る

> 「危険なものを並べて塞ぐ」は必ず漏れる。「安全なものだけ通す」に反転する。

**起きたこと**: `guard.mjs` で `git worktree remove --force` を止める判定を書いたところ、
**22 巡**かけても抜け道が尽きませんでした（語順 → グローバルオプション → 省略形 → 引用符 →
ANSI-C → 行継続 → サブシェル → リダイレクト → `env -S` → `!` → 改行 → `bash -c` …）。
**そのうち約半分は、前巡の修正自身が作った穴**で、過剰ブロックも 4 回。最終的に取り下げました（[D17](./decisions.md)）。

対照的に、env ファイル保護は**列挙をやめて原則拒否に反転**したら一発で解決しました。

```
✗ 列挙:  .env / .env.local / .env.*.local / .env.production / ...
         → .env.staging .env.preview .env.prod が素通りしていた（実測）
✓ 原則:  .env* は原則拒否。通すのはテンプレート（.example / .sample）だけ
```

**この PR 群の中だけで、手で並べたリストが 4 つ漏れました** ——
関数名・`prosecdef` 絞り込み・env ファイル名・RLS 確認テーブル。

### V3. 起きないようにする。見つけるのは次善

> 検知より構造。事故が「起こり得ない」形を選ぶ。

**起きたこと**: プロトタイプを実コードで作ったとき、以下が**実際に起きました**。

| プロトに置いたもの | 実際に起きたこと |
| --- | --- |
| `RecordForm` | 実 Supabase Storage へアップロードしていた |
| `FeedbackWidget`（レイアウト継承で自動的に入る） | 実テーブルへ insert していた |
| `AppHeader` | 実セッションのログアウトが動いた |
| `PhotoGallery` | 実記録へのリンクが張られていた |

**静的 HTML ではこの 4 つが原理的に起きません**（バックエンドへの経路が存在しない）。
これが [D24](./decisions.md) の決め手です。

判断の型: **再現ミスは見れば分かる。本物を壊す事故は気づかないうちに起きる。**
同じ確率なら、後者を構造的に潰せる選択肢を取ります。

### V4. 確認は「失敗が失敗に見える」形にする

> 壊れているか確かめる操作が、壊れていたときに「無事」に見えるなら、それは確認ではない。

**起きたこと**: これを **6 回**踏みました。すべて `verify-backend.md` に書いた「確認手順」です。

| 書いていた確認方法 | 壊れていたとき何が見えるか |
| --- | --- |
| アプリ画面で別世帯のデータを開く | RLS の手前で `householdScopeFilter` が効き、**常に自分の世帯しか出ない** |
| JWT を取って API を直接叩く | 認証失敗時に `Bearer null` で**空が返り「分離できている」ように見える** |
| `pg_policies` を読み比べる | 出るのは**呼び出しだけ**。`has_household_role` が `return true` でも全項目が通る |
| `schemaname = 'public'` で絞る | **写真を守っている `storage.objects` が対象外**になる |

さらに最悪の形が 2 つ出ました。**正しい本番を drift と報告し、従うと運用者がセキュリティを下げる**手順です
（「CRUD 4 種を揃えろ」→ 意図的に無い権限を足させる／「世帯ヘルパーに直せ」→
世帯メンバーが互いの Google refresh token を読めるようにさせる）。

**帰結**: 手順を削除し、分離の担保は **pgTAP**（嘘になった瞬間に CI が落ちる）に一本化しました。
[D25](./decisions.md) で受け入れ条件を E2E テストにするのも同じ理由です。

### V5. 机上で収束させない。一周回して実物で確かめる

**起きたこと**: Codex のレビューを **36 巡**回しましたが、同種の不整合は尽きませんでした。
指摘は最後まで「文章の粗ではなく、**実際になぞると壊れる箇所**」でした。

そして誤りの型は 4 つに収束し、うち 2 つは
**「実際に一周すれば最初の 30 分で出る」**ものでした（表示専用に見えて実は書き込む／
片方だけ直して対が嘘になる）。

**帰結**: 新機能は仕様を文章で固める前に実機で触ります（[D24](./decisions.md)）。
CI の整備も、先に 1 機能を通してから組みます —— 机上で組むと同じことになるからです。

### V6. 測ってから決める

> もっともらしい根拠ほど、測ると崩れる。

**起きたこと**: 静的 HTML を却下した根拠 2 本が、測ったら**両方とも崩れました**。

| もっともらしかった根拠 | 実測 |
| --- | --- |
| 「デザイントークン・ダークモード・セーフエリアは `import` でしか手に入らない」 | **誤り。** 全部 `:root` の素の CSS 変数と `@media (prefers-color-scheme: dark)` / `env(safe-area-inset-*)`。React 非依存 |
| 「静的 HTML は実装時に 100% 捨てる」 | **回避できる。** Tailwind CLI に `@source` で単体 HTML を渡すと **55ms / 8.8KB** で必要な CSS が出る |

どちらも「たぶんそうだろう」で 1 度は決定になっていました。

### V7. 決定は覆してよい。ただし理由を残す

> 間違いは直す。「なぜそう決めたか」「なぜ覆したか」は消さない。

**起きたこと**: D15（実コードプロト）を D24（静的 HTML）で覆しました。
このとき **D15 を削除せず、取り消し線で残し、誤っていた根拠も残しました**。

理由は単純で、消すと**半年後に同じ検討をやり直す**からです。
このリポジトリには実例があります —— `76a2406` は、半年前に「未決事項」へ書いた論点を
人間が読み返して決着させたコミットです。**読み返されるのは未決事項と却下理由**であって、
現状の仕様ではありません。

D ログの規約「**欠番にしない・振り直さない**」も同じ理由です（commit 件名から参照されるため）。

## この文書自体の扱い

V1 を自分に適用すると、本書は「**コードから復元できないもの**」なので残す側です。
ただし **`CLAUDE.md` / `AGENTS.md` には全文を置きません**（二重管理を作らないため）。
本体はここ 1 箇所、他はポインタだけです。

新しい原則を足すときは、**実際に起きたことを根拠として書けるときだけ**にしてください。
根拠のない一般論を足すと、その時点で本書は「誰も読まないもの」になり、V1 の言うとおり腐ります。
