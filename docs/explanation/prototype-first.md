# プロトタイプ駆動をなぜこの形にしたか

新機能の画面・挙動を先に形にして合意し、そこから仕様を確定して実装に入る。
その「先に形にする」手段として **使い捨てブランチの実コードプロトタイプ**を選んだ理由と、
却下した案を残します。

手順そのものは `.claude/skills/prototype/SKILL.md` が正です（本書は「なぜ」だけを扱います）。
関連: [design-decisions.md](./design-decisions.md) / [decisions.md](./decisions.md)

---

## 1. 埋めようとしている穴

現行フローは
`vision-and-roadmap.md`（機能カタログ）→ `phase-N-use-cases.md`（UC-xx ＋受け入れ条件＋D 決定ログ）
→ GitHub Issue → PR → main マージ＝本番リリース。

**この鎖に UI/UX の成果物が 1 つも無い。** 受け入れ条件はほぼ全て RLS / サーバー挙動の語彙で書かれ、
UI に触れるのは `UC-A06「role 別に UI を出し分ける」` の 1 行だけ（しかも「UI は補助」と注記）。

文章の仕様書は情報は伝えられるが、**画面レイアウトと触り心地は伝えられない**。
mfmf は PWA で、価値は「スマホで片手で記録できるか」に集中しているので、この穴は小さくない。

## 2. 却下した案 A: `mocks/` に静的 HTML を置く

最初に検討した案。HTML / CSS / JS だけで画面を組み、リポジトリの `mocks/` に置いて残す。

**却下理由 1: mfmf では実装プロトタイプの方が速い。**
`src/app/gallery/page.tsx` は 99 行で、**約半分がデータ取得**。固定配列に差し替えれば 50 行前後で画面が立つ。
`AppHeader` / `PhotoGallery` / `RecordForm` / デザイントークン / ダークモード / セーフエリア /
フォーカスリングは**すべて `import` で手に入る**。
同じ画面を静的 HTML で作ると markup と JS を書き起こすことになり、しかも**実装時に 100% 捨てる**。
既存コンポーネントが十分に育った今のリポジトリでは、「モックの方が速い」という前提が成り立たない。

**却下理由 2: 情報量が足りない。**

| 得たい情報 | 静的 HTML | 使い捨てブランチ |
| --- | --- | --- |
| レイアウト・配色 | ○ | ○ |
| 画面遷移 | △ 手で `href` を繋ぐ | ◎ 本物 |
| 空 / 大量 / エラー状態 | △ 手で複製 | ◎ 配列を差し替えるだけ |
| ダークモード | △ | ◎ 自動追従 |
| **実機 PWA の触り心地**（セーフエリア・IME・片手操作） | **×** | ◎ |
| 実装への持ち込み | × 全捨て | ◎ そのまま育てられる |
| 3 案の並列比較 | ◎ | △ → 1 ブランチ内の複数ルートで解決 |
| ゼロからのラフスケッチ | ◎ | △ → 発散段階はリポジトリ外で解決 |

静的 HTML が勝つ 2 項目は、どちらも**リポジトリに置く必要がない**。

**却下理由 3: 7 個目の腐敗候補になる**（→ §4）。

**却下理由 4**: Claude Code 作者 Boris Cherny の発言が否定しているのは、PRD **と静的モックの両方**だった。

> *"There's just no way we could have shipped this if we started with **static mocks** and Figma **or** if we started with a PRD."*

代わりに置かれたのは**動くプロトタイプ**であって、モックではない。

## 3. 却下した案 B: Spec Kit / Kiro / OpenSpec の導入

仕様駆動開発ツールで requirements / design / tasks を生成させる案。

**却下理由**: n=1 の個人プロジェクトには過剰。
Scott Logic が同一機能を 2 通りで実装した実測では、Spec Kit 側が Markdown 2,500 行・
人間レビュー 3.5 時間で**約 10 倍遅く**、*"duplicative documentation without improving code quality
or reducing bugs"* と結論している。marmelab は「現在日時を表示するだけで 8 ファイル 1,300 行の Markdown」を報告。

既存の `UC-<領域><連番>` ＋ D 決定ログが、既に十分軽い仕様フォーマットとして機能している。

## 4. ドキュメントを「増やさない」判断の根拠

このリポジトリには、ドキュメントの寿命に関する観測結果が既に出ていた。

| ドキュメント | commit 数 | 最終更新 | 状態 |
| --- | --- | --- | --- |
| `phase-3-5-use-cases.md`（決定ログを含む） | 16 | 2026-07-05 | **正確** |
| `design-decisions.md` | 4 | 2026-06-30 | 陳腐化していた |
| `AGENTS.md` | — | 2026-06-30 | 陳腐化していた |

S1〜S5 が完了しているのに、`CLAUDE.md` / `AGENTS.md` / `design-decisions.md` / `README.md` /
`architecture.md` / `features.md` の 6 箇所が「`household_id` は持たず `owner_id` ベース」等の
古い記述のままだった（うち前 3 者は本書と同じ PR で修正）。

**腐った側は、全部「誰も読まないから腐った」。**
腐敗は規律不足の証拠ではなく、そのドキュメントが不要だった証拠。
7 月に S3/S4/S5 を実装したとき `design-decisions.md` を開いていれば、嘘に気づいていたはず。

一方 `phase-3-5-use-cases.md` が生き残ったのは、**荷重がかかっていた**から。
直近 60 commit のうち 12 件が UC-xx / Dx を件名で引用しており、Issue の元ネタでもある。

加えて **1 日あたり 10〜16 commit**（S3/S4/S5 が約 3 日）という速度では、
手で同期する工程は構造的に必ず飛ばされる。規律で解決できる問題ではない。

→ **だからプロトタイプは「残さない」形にした。** 永続化するのは決定ログ 1 行だけで、
リポジトリに新しい成果物を増やさない。ドリフト源が原理的に発生しない。

## 5. では、何を残すのか

情報を「コードから復元できるか」で分けると、残すべきものが決まる。

| 種類 | 例 | 復元可能？ | 方針 |
| --- | --- | --- | --- |
| 現状の仕様 | 画面一覧・機能一覧・データモデル | **可能**（AI が数秒で） | 書かない・維持しない |
| AI が毎回読む前提 | `CLAUDE.md` / `AGENTS.md` | 可能だが**コードより先に読まれる** | 最小限にし、古いものは**バグとして直す** |
| **決定と却下理由** | D1〜D14、未決事項 | **不可能** | **1 行で残す**（[decisions.md](./decisions.md)） |

コードは勝った案しか語らない。負けた案とその理由は、書かなければ永久に失われ、
半年後に同じ議論を再演することになる。

「過去の仕様を人間が読み返すフロー」が実在する証拠もこのリポジトリにある。
`76a2406 世帯削除(UC-H09 一部)とアイデンティティ連携の方針確定（#117 §3・§4）` は、
半年前に §7「未決事項」へ書いておいた論点を読み返して決着させたコミット。
読み返されるのは**未決事項と却下理由**であって、現状の仕様ではない。
