# 3 案の多観点評価

[notes.md](./notes.md) の 3 案を、UI/UX を最重視した重み付けで評価する。

- **案 A バックアップ型** — アプリが正。保存後にドライブへ控えを作る。表示は常にアプリ側
- **案 B 引っ越し型** — 原本はドライブ・サムネのみアプリ。原本タップ時だけプロキシ経由
- **案 C 毎回選ぶ型** — 保存のたびに「アプリ / ドライブ / 両方」を選ぶ

---

## 1. 評価軸と重み

重みは「ユーザーが不便なく安心して使えること」を最上位に置いた。
**スコアは客観的な事実ではなく、この重み付けを明示するための道具**として読む。

| 観点 | 重み | 何を見るか |
| --- | :---: | --- |
| **UI / UX・安心感** | **5** | 手数が増えないか。写真が消えたように見えないか。失敗が怖くないか |
| **仕様の分かりやすさ** | **4** | 家族に一文で説明できるか。写真ごとに挙動が違わないか |
| **実装の複雑さ / バグリスク** | **4** | 分岐の数。バグったとき安全側に倒れるか危険側に倒れるか |
| 可用性（止まらないか） | 3 | 外部が落ちたときに何が使えなくなるか |
| 性能（遅くならないか） | 3 | 一覧の速さ。原本を開くまでの待ち |
| データ冗長化 | 3 | 写真が失われる単一障害点が残るか |
| セキュリティ / プライバシー | 3 | 攻撃面が増えるか。世帯・ゲストの分離を壊さないか |
| コストパフォーマンス | 3 | ¥0 運用を維持できるか。Supabase Free 1GB の壁 |
| 機能要件の充足 | 2 | 世帯共有・ゲスト・viewer・容量拡張の要求を満たすか |

評価記号: **◎ 4 点 / ○ 3 点 / △ 2 点 / ✗ 1 点**（満点 120 点）

## 3. 案ごとの メリット / デメリット（チャンス / リスク）

### 案 A: バックアップ型

| | 内容 |
| --- | --- |
| **メリット** | ・**今の体験が 1 ミリも変わらない。** 連携してもしなくても、切っても、表示は同じ<br>・説明が一文で終わる（「アプリに保存し、ドライブにも控えを作ります」）<br>・「ドライブだけにある」が原理的に起きず、**状態が 4 つ → 3 つに減る**<br>・**バグが安全側に倒れる**。同期が壊れても写真は見え続ける（未同期バッジが出るだけ）<br>・定義上 2 重化。思い出の単一障害点対策そのもの<br>・ドライブ通信は保存時のみ。レートリミットに当たる経路が無い |
| **デメリット** | ・**容量問題を解決しない。** Supabase Free 1GB は今と同じ速度で減る<br>・同じ画像を 2 か所に持つ（ユーザーのドライブ容量も食う）<br>・「バックアップしたのに、アプリの容量が減らないの？」という素朴な疑問が出る |
| **チャンス** | ・同期エンジン（直アップロード・バックオフ・チェックポイント）は**案 B の部品と同一**。捨てにならない<br>・エクスポート機能（roadmap I）への足がかりになる |
| **リスク** | ・**1GB の壁は確実に来る**（1600px JPEG ≒ 400KB → おおよそ 2,000〜3,000 枚）。<br>　壁に当たると**新規保存ができなくなる＝アプリが止まる**。到達前に案 B へ進む前提が要る |

### 案 B: 引っ越し型

| | 内容 |
| --- | --- |
| **メリット** | ・**容量問題を実際に解決する唯一の案**（アプリ 32MB / ドライブ 1.8GB のような比率になる）<br>・一覧はサムネなのでドライブ通信 0。スクロールしても増えない<br>・**「どちらにも無い」でもサムネが残る**ので、写真が消えたようには見えない<br>・`roadmap.md` §4 の当初構想と一致 |
| **デメリット** | ・**説明が難しい。**「原本はあなたのドライブ、表示用の小さい画像はアプリ」を家族全員に伝える必要<br>・ゲスト・未連携メンバーの写真は原本がアプリに残る＝**混在が正常**という追加説明<br>・「誰のドライブか」の決着が必須（D10）<br>・原本を開くたびにプロキシ往復（1〜3 秒の待ち） |
| **チャンス** | ・Supabase Free のまま長く運用できる（¥0 方針の延命）<br>・原本の解像度を落とさずに保存できる（今は 1600px に縮小している） |
| **リスク** | ・**バグが危険側に倒れる。** 表示経路がドライブに依存するので、認可・トークン・プロキシのどれかが壊れると**写真が見えなくなる**<br>・**冗長化ではなく引っ越し。** ユーザーがドライブで消したら原本は失われる<br>・他メンバーのトークンで配信する経路は、認可を間違えると**他世帯へ漏れる**<br>・一括移行が最も事故りやすい工程（Vercel Hobby にジョブ基盤が無く、クライアント駆動になる） |

### 案 C: 毎回選ぶ型

| | 内容 |
| --- | --- |
| **メリット** | ・自由度が最大。ユーザーが完全に制御できる<br>・「勝手にドライブへ送られる」という不安が原理的に生じない |
| **デメリット** | ・**保存のたびに選択が挟まる。** 写真を残す手数が増え、アプリの目的（続けられること）と正面衝突<br>・**4 状態が本当に全部混ざる。** 写真ごとに挙動が違い、一覧にバッジが並ぶ<br>・家族で設定がばらつき「あの写真どこ？」が起きる<br>・「ドライブのみ」の写真は一覧でも通信が要る |
| **チャンス** | ・「自分で決めたい」という要求は、**設定画面での 1 回きりの選択**にすれば案 A / B でも満たせる（毎回である必要が無い） |
| **リスク** | ・**案 A と案 B の両方の経路を実装し、常に両方を動かす**必要がある。分岐が写真単位でテストが組み合わせ爆発<br>・障害時に**どの写真が影響を受けるか予測できない**（説明も復旧も難しい）<br>・仕様が分かりにくく、問い合わせがここに集中する |

## 8. 結論: 案 A で出し、壁が見えたら案 B へ

**提示された優先順位（UI/UX 最優先・複雑さとユーザーの困惑を避ける）では、案 A が明確に勝つ。**

> [notes.md](./notes.md) では案 B を推していた。あちらは「容量問題を解決するのは B だけ」を
> 最重視した結論で、この優先順位では順位が入れ替わる。**評価軸が変われば結論が変わるのが正しい。**

そして重要なのは、**案 A と案 B の実装上の差は「アプリ側の原本を消すか否か」だけ**という点。
A を作れば B の部品はほぼ揃うので、**最初に選ばなくてよい**。

| 段階 | やること | 得られるもの | 判断のタイミング |
| --- | --- | --- | --- |
| **第 1 段** | 案 A（新しい写真をドライブへバックアップ。表示は今のまま） | 冗長化・安心感。同期エンジンの実績 | 今 |
| **第 2 段** | 「フォトから選ぶ」（Picker） | 入力導線の改善。ドライブとは独立に足せる | スコープの審査要否を確認後 |
| **第 3 段** | プロキシ配信＋サムネ生成を足して案 B へ | 容量問題の解決 | **Supabase 使用量が 1GB の 6〜7 割に届いたら** |
| **第 4 段** | 既存写真の一括移行（クライアント駆動・再開可能） | 過去分の容量回収 | 第 3 段の安定後 |

**第 3 段へ進む条件を数値で決めておく**のが肝。1600px JPEG ≒ 400KB なので、
1GB はおおよそ 2,000〜3,000 枚。設定画面に使用量を出しておけば、壁は突然来ない。

案 C は採らない。ただし「自分で決めたい」は、**設定画面での 1 回きりの選択**
（バックアップする / しない）として案 A の中に残っている。
