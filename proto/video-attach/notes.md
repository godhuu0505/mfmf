# 写真 / 動画の保存 — プロトタイプ

記録に**写真と動画をまとめて添付**する。写真欄と動画欄を分けず、
「写真 / 動画を追加」というひとつの欄で受けて、**MIME → 拡張子の順**で処理を分ける。

## 既存の動線に合わせてある

最初のプロトは独自のヘッダーと上部タブを持つ別物だったので、既存アプリの動線を
読み直して作り直した（2巡目）。踏襲したのは次の通り。

| 既存 | プロトでの再現 |
| --- | --- |
| ボトムタブバー（ホーム / カレンダー / ＋記録 / アルバム / メニュー、D33） | 同じ5スロット。中央の＋が作成導線 |
| ＋ → **クイック記録シート**（チップ・おうち/保育園・ひとこと） | 同じ。写真・動画を付ける入口は「写真つきでくわしく記録する →」 |
| `/records/new`・`?edit=1` は**全画面モーダル**（ヘッダーもタブバーも出ない） | 同じ。キャンセル/保存はセーフエリア直下の固定バー |
| フォームの項目順: 記録元 → ペット → 日付 → 記入者/体重 → **写真** → 本文 → タグ | 同じ。「写真」の位置に「写真 / 動画」を置く |
| **既存の写真は編集画面の「登録済みの写真」タイルから削除**（`PhotoEditTile`） | 「登録済みの写真・動画」として同じ形。追加の欄とは分かれている |
| ホームのカード（80pxサムネ・記録元バッジ・日付・抜粋・タグ・「写真 N 枚」） | 同じ。動画があれば「動画 N 本」と ▶ バッジを足す |
| 記録詳細（バッジ・日付・記入者・編集/…・本文カード・タグ・写真グリッド） | 同じ。写真グリッドに動画が混ざる |
| アルバム（月見出し + `grid-cols-3 gap-1.5 sm:grid-cols-4` + ライトボックス） | 同じ。動画タイルに ▶ と長さ |

**この機能で増えるのは「写真」欄が「写真 / 動画」欄になることだけ**で、
画面や導線は増えない。

## 何を確かめたいか

1. **動画1本の最長は何秒か。** 15 / 30 / 60秒を切り替えて、実際の動画で確かめる。
2. **1記録の動画は何本までにするか。** 1 / 3 / 10本。合計10件のうち動画が何本かで
   容量が二桁変わる（下の「上限の根拠」）。
3. **変換の待ち時間に耐えられるか。** 動画の長さに比例して待つ（実時間 ≒ 長さ × 0.5）。
   写真を数枚選んだあとに動画を足す、という混在の待ちも試せる。
4. **上限に当たったときの断り方。** 11件目・動画の本数超過・長すぎる動画で
   それぞれ別の理由が出る。理由が分かるか。
5. **一覧・詳細・アルバムで写真と動画が混ざった見え方。** ▶ で区別がつくか。
6. **編集画面での消し方。** 「登録済みの写真・動画」から消す既存の形のままでよいか。

## 上限の提案と、その根拠

| 項目 | 提案 |
| --- | --- |
| 1記録の合計 | **10件**（写真＋動画） |
| うち動画 | **3本まで** |
| 動画1本の長さ | **30秒**（ハード上限 60秒） |
| 1オブジェクト | **保存後** 50MB（Supabase Free のハード上限。縮小・変換したあとのサイズで判定） |
| 写真 | 長辺1600px / JPEG q0.8（既存のまま。1枚 ≒ 300KB） |

**「10件まで」を動画にもそのまま適用すると容量が破綻する。**

- 写真10枚 = 約 3MB。**動画10本（各30秒・720p）= 約 75MB。25倍**
- 無料枠 1GB のうち写真・動画に 800MB を充てると:
  - 動画 **3本** まで → 上限まで入れた記録 1件 ≒ 25MB → **約 32記録**
  - 動画 **10本** まで → 1件 ≒ 75MB → **約 10記録**
- 上は最悪ケース。実際は写真数枚＋動画0〜1本なのでもっと入る。

**3本の根拠は弱い**ので、メニュー →「上限を試す」で 1 / 3 / 10 を切り替えられる。

## 拡張子による処理の分岐

| 入力 | 判定 | 処理 |
| --- | --- | --- |
| `image/*`（`.jpg` `.png` `.heic` ほか） | MIME → 拡張子 | 長辺1600px / JPEG q0.8（`imageResize.ts` と同じ素通し条件: `image/` 以外・GIF・SVG は触らない） |
| `video/*`（`.mov` `.mp4` `.m4v` `.3gp` `.webm`） | 同上 | 長さを検査 → **MP4 (H.264/AAC) へ再エンコード** |
| どちらでもない | — | 追加せずエラー表示 |

**MIME だけで判定しないこと。** iOS の `.mov` は `file.type` が空になることがある。

**MP4 (H.264) への統一は必須。** iPhone 標準（高効率）は HEVC/.mov で、
Android Chrome や PC のブラウザで再生できない。

## プロトで再現していないもの

- **動画の変換はしていない。** 進捗は擬似で、圧縮後サイズは
  「長さ × 想定ビットレート（720p=2.0Mbps / 1080p=4.5Mbps）」の計算値。
  待ち時間だけは長さに比例させてある。実装は WebCodecs で再エンコードする想定。
- **写真の縮小は実際にやっている**（長辺1600px / JPEG q0.8）。サイズは実測値。
- サムネイル（poster）はブラウザで1フレーム目を切り出しているが、実装では
  別オブジェクトとして Storage に保存する。
- カレンダー、クイック記録シートの中身（チップ選択・保存）は静止。
- 認証・世帯・権限（viewer は添付できない等）は入れていない。
- **選んだファイルはどこにも送信されない**（`fetch` を書いていない / D24）。

## 実装の前提（合意したら spec.md へ）

- 50MB は Supabase Free の **1オブジェクト**上限。元ファイルではなく、縮小・変換して
  実際に保存するサイズにかかる（4K 写真は 60MB でも縮小後は数百 KB）。
- 一覧・アルバムでは動画本体を読み込まない（`preload="none"` + poster）。帯域は 5GB/月。
- Service Worker は署名付き URL をキャッシュしない（CLAUDE.md の不変条件）。
- DB は `record_photos` を拡張する方向（`kind` / `duration_ms` / `poster_path`）。
  テーブル名が実態と合わなくなるが、リネームは既存 RLS を全部書き直すことになるので別途判断。
