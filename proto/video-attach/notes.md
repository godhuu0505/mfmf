# 写真 / 動画の保存 — プロトタイプ

記録に**写真と動画をまとめて添付**する。写真欄と動画欄を分けず、
「写真 / 動画を追加」というひとつの欄で受けて、**拡張子（MIME）で処理を分ける**。

## 何を確かめたいか

1. **ひとつの欄にまとめて使いやすいか。** 写真と動画が同じグリッドに並ぶ形で、
   何が入っているか把握できるか。削除しやすいか。
2. **動画1本の最長は何秒か。** 15 / 30 / 60秒を切り替えて、実際の動画で確かめる。
3. **1記録の動画は何本までにするか。** 1 / 3 / 10本を切り替えられる。
   合計10件のうち動画が何本かで、容量が二桁変わる（下の「上限の根拠」）。
4. **変換の待ち時間に耐えられるか。** 動画の長さに比例して待つ（実時間 ≒ 長さ × 0.5）。
   写真を5枚選んだあとに動画を1本足す、のような混在の待ちも試せる。
5. **上限に当たったときの断り方。** 11件目、動画の本数超過、長すぎる動画で
   それぞれ別の理由が出る。理由が分かるか。
6. **一覧・ギャラリーでの ▶ バッジの見え方。** 写真と動画が混ざったときに区別がつくか。

## 上限の提案と、その根拠

| 項目 | 提案 |
| --- | --- |
| 1記録の合計 | **10件**（写真＋動画） |
| うち動画 | **3本まで** |
| 動画1本の長さ | **30秒**（ハード上限 60秒） |
| 動画1本のサイズ | 受け入れ 50MB / 保存目標 8MB（720p, H.264） |
| 写真 | 長辺1600px / JPEG q0.8（既存のまま。1枚 ≒ 300KB） |

**「10件まで」を動画にもそのまま適用すると容量が破綻する**ので、動画だけ別に絞っています。

- 写真10枚 = 約 3MB。**動画10本（各30秒・720p）= 約 75MB。25倍**
- 無料枠 1GB のうち写真・動画に 800MB を充てると:
  - 動画 **3本** まで → 上限まで入れた記録 1件 ≒ 25MB → **約 32記録**
  - 動画 **10本** まで → 1件 ≒ 75MB → **約 10記録**
- 実際には毎回上限まで入れるわけではない（多くは写真数枚＋動画0〜1本）ので、
  現実の消費はこれよりずっと少ない。上の数字は最悪ケース。

**3本にした理由**: 保育園の一場面を複数アングルで残すには 1本だと足りないことがあり、
一方で 4本以上を1つの記録に入れる場面が思いつかない。プロトで 1 / 3 / 10 を
切り替えられるので、実際に入れてみて決めてほしい。

## 拡張子による処理の分岐

| 入力 | 判定 | 処理 |
| --- | --- | --- |
| `image/*`（`.jpg` `.png` `.heic` ほか） | MIME → 拡張子の順 | 長辺1600px / JPEG q0.8 に縮小（既存の `imageResize.ts`） |
| `video/*`（`.mov` `.mp4` `.m4v` `.3gp` `.webm`） | 同上 | 長さを検査 → **MP4 (H.264/AAC) へ再エンコード** |
| どちらでもない | — | 追加せずエラー表示 |

**MIME だけで判定しないこと。** iOS から来る `.mov` は `file.type` が空になることがあるので、
拡張子でも判定する（`classify()`）。

**MP4 (H.264) への統一は必須。** iPhone 標準（設定 > カメラ > フォーマット = 高効率）は
**HEVC/.mov** で、これは Android Chrome や PC のブラウザで再生できない。
拡張子を広く受け入れるだけだと「iPhone で撮った動画が Android で見られない」が普通に起きる。

## 触り方

- 右上「上限を試す」で **動画の最長（15/30/60秒）**・**動画の本数（1/3/10本）**・
  **画質（720p/1080p）** を切り替えられる。上限を下げると、すでに入れた動画のうち
  条件を満たさないものはその場で外れる（理由がエラー欄に出る）。
- ＋タイルから**写真と動画をまとめて選べる**（複数選択可）。
- **選んだファイルはどこにも送信されない。** ブラウザの中だけで処理している
  （`fetch` を書いていない / D24）。

## プロトで再現していないもの

- **動画の変換はしていない。** 進捗は擬似で、圧縮後サイズは
  「長さ × 想定ビットレート（720p=2.0Mbps / 1080p=4.5Mbps）」の計算値。
  待ち時間だけは長さに比例させてある（実装の実測が出たら係数を合わせる）。
  実装は WebCodecs で MP4(H.264/AAC) へ再エンコードする想定。
- **写真の縮小は実際にやっている**（長辺1600px / JPEG q0.8）。表示されるサイズは実測値。
- サムネイル（poster）はブラウザで1フレーム目を切り出しているが、実装では
  これを別オブジェクトとして Storage に保存する。
- 写真のタップ（ライトボックス）は既存の `PhotoGallery` があるので作っていない。
- 認証・世帯・権限（viewer は添付できない等）は入れていない。
- PWA スタンドアロン表示・オフライン挙動は Artifact では確認できない（Vercel Preview で）。

## 実装の前提（合意したら spec.md へ）

- **1ファイル 50MB は Supabase Free のハード上限**なので、受け入れ上限はこれを超えられない。
- 一覧・ギャラリーでは動画本体を読み込まない（`preload="none"` + poster）。無料枠の帯域は 5GB/月。
- Service Worker は動画・写真の署名付き URL をキャッシュしない（CLAUDE.md の不変条件）。
- DB は `record_photos` を拡張する方向（`kind` / `duration_ms` / `poster_path`）。
  テーブル名は実態と合わなくなるが、リネームは既存 RLS ポリシーを全部書き直すことになるので
  別途判断する。

## 決まっていないこと（このプロトで潰す）
